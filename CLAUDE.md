## Comment style

Comments documenting a function, method, or class are `/** ... */` blocks, never
`//` line comments — the block form is what editors surface on hover and in
completions, and a `//` above a function is invisible to that machinery. Python
uses the usual `"""docstring"""`.

```js
/**
 * Fire a DOM event into HA's frontend.
 *
 * @param {string} type Event name, e.g. 'hass-more-info'
 */
fireEvent(type, detail, options) {
```

`//` stays correct for statement-level comments inside a body, and for comments
on `const`/variable declarations. When editing existing code that uses `//` on a
function, convert it rather than matching the surrounding style.

## Things that will bite

- **`custom_components/lightening/frontend/app/` is build output.** It's
  gitignored and regenerated by `npm run build`; CI builds it into release tags.
  Never edit it — the source is `frontend/src/`.
- **`manifest.json` says `"version": "0.0.0"` on purpose.** The field is
  mandatory for custom integrations and can't be omitted, but the real version
  is stamped by CI into the release tag only. `0.0.0` is the unreleased
  sentinel: valid SemVer, sorts below every release, and doesn't read as a stale
  real version. Don't "fix" it, and don't add a second copy of the version
  anywhere — the integration reads it back at runtime with
  `async_get_integration(hass, DOMAIN).version`.
- **`HA_TARGET` must not name a specific instance.** It lives in a gitignored
  `frontend/.env.local`; the checked-in default is `homeassistant.local:8123`.
  Keep hostnames of real instances out of the repo.
- **Don't push without being asked.** A push to `master` cuts a release and
  propagates to HACS installs.
